# 源镜像层不做版本留存

## 背景

PIT 研究理想上需要「源端历史版本」——某个报告期的数据在每次修订前后分别
是什么值、每个版本何时可见。

实现方式有几种：源镜像层做 CDC 保留全部变更、做 SCD Type 2 维护有效区间、
或每次采集全量快照。

约束条件：这是单人维护的项目，源端（Wind、Tushare、聚源、朝阳永续）多数
只提供当前值，部分提供公告日。旧仓 `wx2` 没有保留任何修订历史。

## 决策

**PG 源镜像层只反映源端当前状态，不做 CDC、不保留历史版本。**

这是有意的取舍，不是疏漏。

同时做两件补偿：

1. **诚实标记**：契约中 `pit_recoverable: false` 与 `pit_from` 如实记录
   历史缺口。
2. **从现在开始积累**：每个采集批次的原始拉取结果 append-only 归档到
   `var/lake/_vintage/<source>/<dataset>/batch_dt=.../`。

## 理由

1. **CDC 的成本与收益不匹配**。源端多数不提供历史版本，CDC 只能捕获"本
   系统观测到的变化"，而这个信息用 `_vintage/` 归档同样能得到，且实现简单
   得多。
2. **源表结构保持简单**。加了有效区间和版本号的源表，查询变复杂、写入变
   复杂、与源端结构不再一一对应。
3. **归档比 CDC 更完整**。CDC 记录的是入库后的变化，归档的是原始拉取结果，
   后者在标准化逻辑变化后仍然可用。
4. **既成事实无法改变**。旧仓的修订历史已经丢失，无论新系统怎么设计，
   存量数据的 PIT 起算日都是迁移日。承认这一点比假装能补救更有价值。

## 被否方案

| 方案 | 否决理由 |
|---|---|
| 源表做 SCD Type 2 | 源端不提供版本信息时，"有效区间"只能用采集时间构造，那是伪造 |
| 源表做 CDC（触发器或逻辑复制） | 只能捕获本系统观测到的变化，与 `_vintage/` 归档信息量相同但复杂度高得多 |
| 每次采集全量快照进 PG | 存储成本随时间线性增长，且 PG 不适合存大量历史快照 |
| 迁移时用某种规则"补出"历史版本 | 这是伪造历史。见下面的"最危险的错误" |

### 最危险的错误

用 `_ingested_at` 当历史发布时间。存量数据一次性迁入时，`_ingested_at`
全部等于迁移日，用它做 PIT 过滤等于"所有历史数据在迁移日之前都不可见，
之后全部可见"——PIT 事实上失效了，但回测曲线看起来完全正常。

这个错误必须在设计层面堵住，因此有下面的推论 1。

## 代价

1. **源端静默修订不可回溯**。如果 Wind 某天悄悄改了三年前的一个财务数据，
   我们无法知道改前是什么。
2. **存量数据的 PIT 等级只能是 D**。所有 `wx2` 迁入的数据，`pit_from` 都是
   迁移日，此前的可见日不可信。
3. **需要等时间积累**。`_vintage/` 归档要跑一年才有一年的版本序列。这是
   不可加速的。
4. **部分研究做不了**。例如"财报修订对股价的影响"这类研究，在积累足够
   版本序列之前无法做。

## 推论

1. **源层的时间字段不得被当作 PIT 依据**。`_ingested_at` 在 schema 层面就
   标注为"非 PIT"，`domain/pit` 的规则引擎不接受它作为 `source_field` 规则
   的字段——除非该数据集是系统上线后才开始采集的，且显式声明为
   `ingest_time` 规则并标注等级 C。
2. **`_vintage/` 归档排在 P1，不排在 P2**。越早开始积累，收益越大；每晚
   一天就永久少一天的版本序列。因此它与存储底座一起启动，不等数据入湖
   完成。
3. **未来若某个数据集确需版本语义**，走「新增旁表 + 契约声明」的扩展路径，
   不改原生表。这条路径预留在设计里，见
   [../domain/temporal-semantics.md](../domain/temporal-semantics.md)。
4. **PIT 等级会随时间提升**。系统上线后采集的数据可以从 C 升到 B（有了
   观测序列），源端原生提供发布时间的可以是 A。等级不是一次定死的。
