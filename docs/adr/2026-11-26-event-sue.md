# event_sue 迁移口径

## 背景

`event_sue`（标准化未预期盈利，`pf_single_event_sue_1_mean_pos`，方向 +1）迁移自旧仓
`factors/factor_event_2.py` 的 `event_sue`。输入是朝阳永续三源业绩公告（业绩预告
`fin_performance_forecast`、业绩快报 `fin_performance_express`、正式财报 `fin_income_gen`）
与 `fin_income_gen` 的历史归母净利润序列。它是 Current-20 中第一个**事件驱动稀疏**因子，
与 did_ratio/nap_adj_ratio 的逐日横截面形态根本不同，带来了四个需要裁定的新问题。

## 决策

### 1. 事件驱动稀疏物化形态：event_dt = 公告日，不逐日填

事件因子只在业绩公告发生时产值，不是逐日横截面。`event_dt` = 公告日 `declare_date`；
`knowledge_dt` 由血缘推导并箍到 `event_dt`（财报当天收盘后可见，与 nap_adj_ratio ADR 决策 4
同语义）。逐事件 PIT：每只事件用自己的 `declare_date` 截止历史利润序列
（`declare_date <= 事件.declare_date`），不是统一的 as_of——早期事件不能看到晚期才公告的财报。
可见性契约统一 `declare_date`（grade A），与 `rpt_earnings_adjust` 用 `entrytime` 不同——
财报入库及时（负责人 2026-11-26 裁定），研报则滞后明显。

### 2. 同键多报告期聚合：按 (declare_date, asset_id) 求 AVG（2026-11-26 裁定选项 1）

长表唯一键 `(event_dt, asset_id, feature_id, definition_version, param_hash)` **不含 report_period**，
但同一股票同一公告日常同时披露多个报告期（年报+一季报，income 源实测 28,821 例），逐事件会
产生同键冲突。旧仓 wx2 主键含 report_period 保留两行；新仓长表无法容纳。

查证下游消费（`alpha_factory/etf/gateway.py:562`）：读取时 `AVG(CAST(event_sue AS float))
GROUP BY confirm_date, stock_code`——下游本就按 `(confirm_date, stock_code)` 求平均，report_period
维度在消费端从未被利用。因此物化时复现该语义：同 `(declare_date, asset_id)` 的多个 sue 求平均
写一行。血缘取参与平均的所有事件输入并集。**不改长表格式**，因下游真实粒度就是
`(confirm_date, stock_code)`，与长表键一致。实证：600000.SH 2024-04-30 年报+一季报
AVG=(1.5405−0.5467)/2=0.4969，与物化值一致。

### 3. 空批次语义：区分合法空与异常空（2026-11-26 裁定）

事件月份过滤只取 `{1,2,3,4,7,8,10}` 披露期（剔除业绩修正），5/6/9/11/12 月源数据本无财报
declare（实证 2019-05 事件候选=0）。这导致非披露月整月无事件、`write_feature_values` 报
"没有可写入的因子行"；日更每天跑，绝大多数交易日无披露，不解决则日更完全不可用。

裁定：materialize 层按 **`candidate_count`（月份/时效过滤后的候选事件数）** 区分，而非产出是否为空：

- **合法空**：候选为 0（非披露期本无事件，业务事实）→ 返回 `(0, digest)` 成功不写文件，
  run log 记 `row_count=0`。
- **异常空**：候选非 0 却全部未产值（算法/数据问题）→ raise fail-closed。

区分点是"候选是否为空"，不吞"有事件却全失败"。反向验证：全历史回填中披露期
（01/02/03/04/07/08/10）63 月全部产值、无一个空批次；43 个非披露月全部 row_count=0 合法空。

### 4. golden 差异 = 财报修订快照时差（2026-11-26 裁定通过）

算法与 pandas 精确复现零分歧（300 随机对拍 148 产值一致 + 152 双方 None；002368 端到端
独立 SQL 吻合）。但 wx2 对拍 1296 只中 28 只（2.2%）有差异，根因不是算法：

**wx2 `stock_event_sue` 是用计算时点（insert_time，如 2025-10-16）的 `fin_income_gen` 快照算的**，
而财报会被朝阳永续后续修订（1003 调整版），PG 是当前最新镜像。输入数据时态不同导致 sue 不同。
实证：002368 的 2022Q4 `1001=6358万 vs 1003=6221万`（2026 修订）；002424 的 2023Q4
`1001=-2401万 vs 1003=-4.14亿`（2025 重述），sue 差 10.19。

这类**数据快照时差**无法通过算法复现（是数据的时态属性），且新仓用当前可见数据重算本就是
更正确的 PIT 语义——wx2 在 2025-10 算 2024-04 的事件本身违背了"事件后尽快产出"的研究意图，
新仓逐日增量会在事件次日就算。对拍一致率 97.8%（1268/1296）+ 快照时差 28 + 缺失 0，
负责人裁定通过。差异登记为"快照时差"类别，不算不一致。

## golden 对拍结果

fixture `tests/golden/market_data/event_sue/20240430.json`（wx2 逐 report_period 行 1769 行）。
2024-04-30 共 1296 只：**一致 1268（97.8%）+ 快照时差 28（2.2%）+ 缺失 0**。对拍口径：
wx2 同股多 report_period 行先求 AVG（复现下游消费粒度）再比对。

## 遗留：is_valid/sequence 未过滤

事件候选读取**不过滤 `is_valid`、不去重 `sequence` 修订**（复现旧仓原样读取全量镜像）。
forecast 有 2,049 行 `is_valid=0` 作废公告、3,617 个同键多行。这是否影响结果未单独核验——
golden 一致率 97.8% 说明影响很小，但作为已知口径差异登记，后续若发现异常值可回溯此项。
