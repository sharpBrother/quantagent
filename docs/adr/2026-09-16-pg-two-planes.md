# PostgreSQL 分为研究数据面与控制状态面

## 背景

设计原则定为「PostgreSQL 只存原始数据，派生数据一律走 Parquet」。但这条
原则立刻遇到一个反例：**调度水位、批次登记、运行日志、告警状态放哪？**

它们不是原始数据，也不是研究派生数据。它们需要事务和并发写入，因此不适合
Parquet；Dagster 的运行存储本身就要一个关系库。

如果笼统地说"PG 只存原始数据"，这些东西就无处安放，实际结果会是混进源表
或另建一个第三方存储。旧仓 `wx2` 就是前者——一个库里混着源镜像、派生因子、
策略结果、调度日志四类职责，`scheduler_job_run_log`、`task_moniter`、
`task_error_detail` 与源表平级共存。

## 决策

PostgreSQL 上划分两个**互不混用**的逻辑面，各自有独立的 schema 前缀、
写入者与规则。

### 研究数据面 `src_*`

schema：`src_wind`、`src_tushare`、`src_jydb`、`src_suntime`、`src_macro`。

- 只允许 `quantagent.ingest` 写入
- 只存源数据原生结构，禁止任何业务加工
- 派生数据一律不进 PG

### 控制状态面 `ops_*`

调度水位、批次登记、运行日志、告警状态，以及 Dagster 自带的运行存储。

- 不是研究数据，不对 lake 供数
- **任何研究查询都不得读取它**
- 重新建模，不照搬旧结构

### 迁移序列分开

`db/migrations/src/` 与 `db/migrations/ops/` 是两条独立的迁移序列。

## 理由

1. **"PG 只存原始数据"得到准确表述**。它约束的是研究数据面；控制状态另有
   归属，不靠混进源表解决。
2. **变更频率与风险等级不同**。源表结构跟随外部源变化，控制状态表跟随编排
   能力变化。混在一条迁移序列里会让"改调度表"和"改源镜像"互相阻塞——改一个
   低风险的调度字段要走高风险的源表迁移流程。
3. **可以按面授权**。研究查询的数据库账户可以只授予 `src_*` 的读权限，
   物理上杜绝"研究结论依赖了调度状态"这类污染。
4. **Dagster 原生支持**。dagster-postgres 需要一个库，给它独立 schema 比
   给它一个独立实例更简单，比让它和源表混住更干净。

## 被否方案

| 方案 | 否决理由 |
|---|---|
| 控制状态混进源表 schema | 复刻 `wx2` 的混层问题，且无法按面授权 |
| 控制状态放 SQLite | 并发写入能力不足；且多一套存储技术 |
| 控制状态放 Parquet | 需要频繁小量更新，Parquet 不适合 |
| 控制状态放独立 PG 实例 | 单人项目多维护一个实例，成本不划算；schema 隔离已够 |
| 只用一个 schema 靠表名前缀区分 | 无法按 schema 授权；迁移序列也无法分开 |

## 代价

1. **配置项翻倍**。两套连接参数（`QUANTAGENT_PG_SRC_*` 与
   `QUANTAGENT_PG_OPS_*`），即使指向同一实例。
2. **跨面查询不便**。想知道"某张源表上次成功采集是什么时候"需要读两个面。
   这是刻意的不便——如果方便，研究查询就会开始依赖控制状态。
3. **两条迁移序列需要各自维护**。

## 推论

1. `src_<source>._batch` 旁表属于**研究数据面**，不属于控制状态面。它记录
   的是"这批源数据的来源信息"，是源数据的元数据；而 `ops_*` 记录的是"系统
   运行状态"。区分标准：排查数据口径时需要它，就在 `src`；只有排查调度问题
   时需要它，就在 `ops`。
2. 控制状态表必须有主键。旧仓 `task_moniter` 是 `to_sql(append)` 无约束
   写入，且表名拼写错误，重建时一并修掉。
3. 告警的接收人与地址进配置，不硬编码。旧仓写死了内网 IP 与接收人工号。
