# 时间语义：三条时间轴与四种时间形态

这是整个系统里最容易出错、且出错最不容易被发现的部分。因此单独成章，且
把「不允许怎么做」写得和「应该怎么做」一样详细。

配套文档：[pit-rules.md](pit-rules.md) 讲可见性规则本身。

## 一、三条独立的时间轴

| 轴 | 字段 | 回答的问题 | 来源 |
|---|---|---|---|
| 业务时间 | `event_dt` / `period_end` / `valid_from`–`valid_to` | 数据描述哪一天、哪个报告期、哪段有效区间 | 源端业务字段 |
| 来源发布时间 | `published_at` | 市场何时能知道这个版本 | 仅当源端原生带有（公告日、官方发布日历）时才有值 |
| 系统采集时间 | `ingested_at` | 本系统何时实际取得 | 采集批次 |

### 三者都不是 PIT

`knowledge_dt`（可见日）是这三者经由**显式规则**计算出的派生结果，不是任何
一个字段的别名。

这一点必须反复强调，因为三种误用都很常见：

| 误用 | 后果 |
|---|---|
| 把 `event_dt` 当可见日 | 引入未来信息。财报的报告期末日远早于公告日 |
| 把 `published_at` 当可见日 | 忽略了"当日几点发布"和"下一个交易日才能用"的差别 |
| 把 `ingested_at` 当可见日 | **最危险**。存量数据一次性迁入时它全部等于迁移日，用它做 PIT 等于伪造历史 |

第三种尤其危险，因为它不会产生明显异常——回测曲线看起来正常，只是所有
历史样本的可见日都是迁移日，PIT 过滤事实上失效了。

### published_at 缺失就是 NULL

源端没有原生提供发布时间时，`published_at` 必须是 `NULL`。

**不允许推测填充**，包括：不允许用 `event_dt + N` 推算，不允许用
`ingested_at` 代替，不允许用同类数据的平均延迟估算。schema 层面也不给它
默认值。

理由：一个 `NULL` 是明确的"不知道"，可以被规则的 `fallback` 分支正确处理；
一个推测值是不明确的"可能对"，会沉默地污染所有下游。

推测延迟这件事属于**规则**，可以写成 `fixed_lag(T+N)` 或
`statutory_deadline` 规则并标注相应的 `grade`，但它不能写进数据字段。
规则可审查、可枚举、可批量修改，字段做不到。

## 二、四种时间形态

数据集在契约里必须声明 `temporal_kind`，它决定这个数据集的键与查询语义。

### point_event：点事件

- 例：日行情、成交、指数点位
- 键：`(event_dt, asset_id)`
- 查询：按日期精确匹配或区间过滤
- 修订：一般没有；若源端会修订历史行情，应改归 `period_with_revision`

### period_with_revision：期间型且可修订

- 例：财报、宏观指标、一致预期
- 键：`(period_end, asset_id, version)`
- **同一报告期允许多个版本共存**
- 查询：给定 `as_of`，取该报告期在当时可见的最新版本

这是最复杂的一类。三个必须处理的情形：

1. **同期多版本**：2025Q1 的净利润在快报、正式报告、修订后各有一个值。
   查询"2025年5月1日时我知道的 2025Q1 净利润"必须返回当时可见的那一版。
2. **跨期修订**：修订 2024Q3 的数据可能在 2025 年发生。修订版的
   `period_end` 是 2024Q3，`published_at` 是 2025 年。
3. **版本不可得**：源端只给当前值，不给历史版本。这时**契约必须如实声明
   为「版本不可得」**，`pit_recoverable: false`，`pit_from` 记录起算日。

第三种情形的处理原则：**不得用采集批次伪造版本序列。** 每天采集一次并把
批次号当版本，得到的是"本系统观测序列"，不是"市场可见版本序列"。两者的
区别在于：前者的时间戳是我们的，后者的时间戳是市场的。混用会让"某日市场
知道什么"变成"某日我们抓到了什么"。

本项目不做源拉取的观测归档，因此也不把「本系统何时首次看到这个值」当成
B 级 PIT 来源。无发布时间的数据集停在 C/D。见
[../adr/2026-09-17-no-source-vintage-archive.md](../adr/2026-09-17-no-source-vintage-archive.md)。

### interval：有效区间型

- 例：指数成分、行业归属、停复牌、ST 状态、股本结构变更
- 键：`(asset_id, valid_from)`，配 `valid_to`
- 查询：按区间命中，`valid_from <= target_dt < valid_to`

要点：**区间必须显式建模，不能压成当前值。** 旧仓有些成分与分类数据只存
当前状态，导致回测时用今天的行业分类去算三年前的行业中性化——这是典型的
未来信息泄漏，且泄漏程度不可估计。

区间数据自身也有可见性问题：指数成分的调整通常提前公告、延后生效，所以
`published_at`（公告日）与 `valid_from`（生效日）是两个不同的日期，两者都
要保留。Wind `AINDEXMEMBERS*` 源表没有独立公告日，现役下游用
`S_CON_INDATE` / `S_CON_OUTDATE` 对 `as_of` 闭区间切片；新仓延续这条，
不编造公告日。

### snapshot：时点快照

- 例：持仓、股东户数、融资余额
- 键：`(snapshot_dt, asset_id, ...)`
- 查询：取不晚于目标日的最近快照
- 注意：快照之间的状态是未知的，不是"保持不变"。需要插值时必须显式声明
  插值方式，不默认前向填充

## 三、原生结构与技术元数据如何兼容

源镜像层要同时满足两个要求：结构与源端严格一致，以及系统侧能追溯批次。
解法是把两类信息分开放。

### 源字段不动

字段名、类型、语义与源端严格一致。**不改含义、不加业务字段。**

理由：一旦在采集层做了加工，就无法回答"源端到底给了什么"。而排查口径差异
时，这是第一个要问的问题。

### 系统侧信息走统一前缀的技术元数据列

| 列 | 含义 |
|---|---|
| `_batch_id` | 采集批次标识，外键指向 `src_<source>._batch` |
| `_ingested_at` | 本系统采集时间。**不是 PIT 依据** |
| `_row_hash` | 行内容哈希，用于幂等与变更检测 |

下划线前缀是为了与源字段区分——任何源端都不会用 `_` 开头的字段名。

### 批次登记走旁表

`src_<source>._batch`：拉取窗口、源端游标位点、行数、digest、成功或失败
原因。

这张表回答"这批数据是什么时候、用什么参数、从哪个位点拉的"，不侵入源表
结构。

### 扩展路径

未来若某个数据集确需版本语义，走「新增旁表 + 契约声明」：新建
`src_<source>.<table>_version` 旁表记录版本序列，契约里声明该数据集的
`temporal_kind` 为 `period_with_revision` 并指向旁表。**不改原生表。**

删除记录同理：源端删除的行不物理删除，在旁表记一条删除事件。

## 四、历史版本的补齐策略

### 已丢失的不可能补出

历史修订版本一旦丢失，不可能靠迁库补出。旧仓的 `wx2` 没有保留源端修订
历史，因此所有存量数据的 PIT 起算日就是迁移日，这是既成事实。

诚实记录的方式是契约里的 `pit_recoverable: false` 与 `pit_from`，见
[pit-rules.md](pit-rules.md)。

### 不做观测归档

不把每次拉取的原样结果另存一份。源表体量大，源端静默修订视为可接受误差。
没有这份归档，就不能靠「我们何时首次观测到」把无发布时间的数据集从 C 抬
到 B；也不得改用 `_ingested_at` 或批次号来冒充。取舍见
[../adr/2026-09-17-no-source-vintage-archive.md](../adr/2026-09-17-no-source-vintage-archive.md)。

## 五、常见错误清单

供 code review 时对照：

1. 用 `event_dt` 直接过滤，没有 `as_of`
2. `published_at` 字段被填了推测值
3. 用 `_ingested_at` 做 PIT 过滤
4. 成分或分类数据只存当前值，没有 `valid_from` / `valid_to`
5. 快照数据被前向填充成连续序列，且未声明
6. 同一报告期的多版本被去重成一条
7. 采集批次号被当作版本号
8. 存量迁入数据的 `pit_from` 未设置
9. 半日市或节假日调整未走 `domain/calendar`，而是硬编码日期
10. 时区未统一——源端给北京时间、系统按 UTC 解析，差 8 小时导致跨日错误
